# Security Guidance

This document provides recommended practices for managing keys, secrets, and incident response.

## Protocol Security

VoteChain V3 implements several protocol-level hardening measures:

- **On-Chain Idempotency**: Every vote includes a `kiosk_nonce` generated by the edge device. The `VotingV3` smart contract rejects any transaction with a previously used nonce, preventing replay attacks.
- **Merkle Root Integrity**: The voter registry is hashed into a Merkle Tree at election start. The root is anchored to the `VotingV3` contract via `setVoterListRoot()`. This "freezes" the electorate — any modification to the voter list would produce a different root, detectable by anyone using the Auditor Toolkit.
- **Sequential Vote Queue**: The backend processes transactions via a sequential queue to prevent Ethereum nonce collisions and improve stability under load.
- **Fail-Safe Reconciliation**: Votes are initially persisted as `PENDING` states in the database. Successful blockchain confirmation triggers an update to the final transaction hash and a `is_confirmed` flag.
- **Session Tokens**: Voting requires a signed `session_token` obtained during biometric check-in, preventing direct API injections without hardware presence.
- **Kiosk Hardware Hardening**: Fingerprint verification is limited to **max 2 attempts** with clear audio-visual feedback to reduce frustration while preventing enumeration.
- **Service Discovery Logic**: The kiosk uses a dynamic discovery mechanism via Supabase, ensuring it can always find the moving target of an Ngrok tunnel backend.

## Secrets Management

| Secret | Purpose | Rotation |
|--------|---------|----------|
| `SERVER_PRIVATE_KEY` | Signs all blockchain transactions | Rotate immediately on compromise |
| `ADMIN_SECRET` | Protects admin API routes | Change periodically |
| `AADHAAR_SALT` | Salts Aadhaar IDs before SHA-256 hashing | **Never change mid-election** (breaks Merkle proofs) |
| `SUPABASE_KEY` | Service-role DB access | Rotate via Supabase dashboard |

## Database & RLS

- **`system_config`**: Restrict UPDATE permissions to the `service_role` to prevent unauthorized backend URL hijacking.
- **`receipts`**: Use unique indexes on `code` and `tx_hash` to maintain audit trail integrity.
- **`voters`**: Aadhaar IDs are salted and hashed (SHA-256) before storage; the primary database contains hashed PII but the blockchain entry is anonymous. Only the Merkle Root (a single 32-byte hash) is stored on-chain.
- **`enrollment_requests`**: [PII PROTECTED] Public read access is strictly disabled. Only the backend `service_role` can access the enrollment queue.

## Incident Response

- **Key Compromise**: Rotate `SERVER_PRIVATE_KEY` and `ADMIN_SECRET` immediately.
- **Salt Compromise**: If `AADHAAR_SALT` is leaked, attackers could attempt rainbow table attacks against the voter database. Rotate the salt and re-hash all voter records.
- **Blockchain Issues**: The `SimpleVoteQueue` logs persistent errors; monitor these for RPC provider failures or gas price spikes.
- **Merkle Root Mismatch**: If the on-chain root doesn't match a locally-computed root, the voter list may have been tampered with. Investigate immediately.
